# ADR-0006: 検証のハーネス

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 検証の層

| 層 | 確かめること | iOS | Android |
| --- | --- | --- | --- |
| 単体 | ロジック、正解データとの一致 (ADR-0002 §2) | Swift Testing | JUnit (JVM) |
| 結合 | 手元で起こしたサーバーとのやり取り | XCTest | JUnit |
| 操作 | 主要な筋書きを、シミュレータとエミュレータで通す | XCUITest | Compose UI Test |

- 結合と操作の層は、`../my` の開発用の構成を起こして使う。その試験用の fake と筋書きのシード (my ADR-0015) も使い、外部のサービスには繋がない。
- 道具の版と細かい構成は、骨組みを作るときにコードで決める。

### 2. 画面は作った過程を知らない評価役が見る

描画した画面は、実装したエージェントではなく、作った過程を知らない評価役のエージェントが見る (my ADR-0169 と同じ考え)。

- 評価の基準は、その OS のガイドラインである (ADR-0002 §6)。
- 両 OS の画面を並べて確かめるのは、ADR-0002 §6 の「揃えるもの」が欠けていないかだけである。見た目の違いは指摘しない。

### 3. 関門

- 検査の入口は 1 つのタスク実行器にまとめる。エージェントにも CI にも、同じタスクで検査を通させる。手元では変更が触れた領域を、CI ではすべてを確かめる (ADR-0012 §3)。
- CI は、Merge Queue を唯一の関門にする (my ADR-0079 と同じ考え)。

## 採らなかった案

- 操作の層だけで確かめる: 実際の動きに近い。しかし遅く不安定で、エージェントの手元の反復が回らない。

## 見直す条件

- 操作の層と評価役のどちらにも捕まらない不具合が、繰り返し出荷されたとき。
- 評価役が見ていない画面の崩れが繰り返し出荷されたとき、画面の層を入れ直す。
