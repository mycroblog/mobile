# ADR-0007: 入口・プロセス・アカウント

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. アプリの単位は画面ではなく、プロセスと入口である

アプリは、本体の外に、OS が別に起動するプロセスや受け口を持つ。どれも、本体の画面の状態に頼らずに働ける作りにする。

| 入口 | iOS | Android |
| --- | --- | --- |
| 通知を受ける | Notification Service Extension (別のプロセス。打ち切りまで約 30 秒) | FCM の受け手 (本体のプロセス。数秒のうちに通知を出す) |
| 通知の操作 (返信・ふぁぼ) | 本体のプロセスがバックグラウンドで受ける | BroadcastReceiver と WorkManager (本体のプロセス) |
| 共有を受ける | Share Extension (別のプロセス。完了の後すぐに終わる) | 共有のインテント (本体のプロセス) |
| リンクを開く | Universal Links、カスタムスキーム | App Links、カスタムスキーム |
| OS の機能から開く | App Intents、Spotlight、Handoff、ウィジェット | アプリのショートカット、ウィジェット |
| 書き込みを終える | background URLSession | WorkManager、利用者が始めた転送 |

- iOS の拡張機能は、本体の部品の組を持ち込まない。使うのは、ドメインの型、API の通信、Keychain、Push の暗号、拡張機能用のアカウントの文脈 (§5) だけである。メモリの上限と、打ち切りの時間に収めるためである。メモリの上限は、Notification Service Extension で約 24 MB、Share Extension で約 120 MB と開発者の間で広く報告されているが、Apple は公表していない (Apple Developer Forums、2026-11-27 に確認)。
- Android では、プロセスがいつ終わっても、どの入口からでも、保存したものから画面を作り直せるようにする (ADR-0008)。

### 2. 外からの入力は、1 つの行き先の値に変えてから扱う

- リンク、カスタムスキーム、通知のタップ、共有、ウィジェット、OS の機能からの起動は、各 OS の 1 か所の入口で、型の付いた「行き先の値」に変える。値はアカウントを含み、保存して後から戻せる。各 OS のナビゲーションは、この値をそのまま、または OS の仕組みの形 (Android では Navigation 3 のキー) に移して使う。
- 入口は、先にアカウントを決め (§3)、次に画面を動かす。アカウントの切り替えを待つために時間を置かない。Ice Cubes は、通知を開くとアカウントを切り替えてから 0.2 秒待って画面を動かす。Pachli は、アカウントの切り替えの最中に画面が乱れたため、振り分けを本体の画面から専用の入口に移した (#1496)。
- 外から来た値は信用しない。入口で検査する。投稿・フォロー・削除のように取り消せない操作は、カスタムスキームから直接は行わず、確認の画面を経る。
- 共有されたファイル (画像・動画) は、入口ですぐにアプリの保存の場所 (iOS ではアプリと拡張機能の共有の場所) に写し、行き先の値は写したものを指す。共有の読み取りの許可は受けた画面に結びつき、プロセスが終わると失われるからである。
- リンクとカスタムスキームの文法 (どの URL が何を開くか) は機能の一部なので、両 OS で揃え、正解データで検査する (ADR-0002 §2)。
- 通知を開いたときの行き先は、通知の ID から決める。`my` の通知の本文にある Web クライアントのパスは使わない。`my` は、クライアントの画面の場所をサーバーが知るべきでないとして、パスを通知の ID だけの形にしている。
- OS に結びつけて検証するドメイン (Universal Links と App Links) は、プロジェクトのドメインだけにする。ほかのサーバーのドメインは、そのサーバーがアプリの検証の文書を置かない限り結びつけられないからである。ほかのサーバーの投稿やアカウントの URL は、アプリの中でタップされたとき、または共有で受けたときに、アカウントのサーバーで検索してアプリの中で開く。開けないときはブラウザで開く。

### 3. アカウントは型で明示し、データの層に「今のアカウント」を置かない

- サインインしたアカウントごとに、そのアカウントの通信・トークン・ストリーミング・保存所をまとめた組 (アカウントの組) を作る。データの層の部品はどれかのアカウントの組の中にあり、ほかのアカウントを参照する手段を持たない。
- 「表示しているアカウント」は、画面の状態としてだけ持つ。iOS ではウィンドウごとに、Android ではアプリに 1 つ持つ。最上位の行き先ごとの積み重ねは、アカウントごとに持つ。保存した画面の状態を戻すとき、サインアウトしたアカウントの行き先は捨て、残っている最初のアカウントにする。
- データの層、通知の受け手、入口は、表示しているアカウントを読まない。入力がアカウントを含まないときは、次の順で決める。
  - アプリの中の操作から来たときは、その画面のアカウントにする。
  - アカウントが 1 つだけなら、それにする。
  - 2 つ以上なら、利用者に選ばせる。表示しているアカウントは変えない。共有したことやリンクを開いたことは、表示中のアカウントで操作したいことを意味しないからである。
- 通知を開いたときは、通知のアカウントで開く。
  - iOS では、そのアカウントを表示しているウィンドウがあれば、最後に使ったものに出す。なければ、新しいウィンドウを開ける状態なら新しいウィンドウを開き、開けなければ前面のウィンドウのアカウントを切り替える。
  - Android では、表示しているアカウントを通知のアカウントに切り替え、通知の行き先の積み重ねの上に、通知の対象を積む。ほかの行き先の積み重ねは残す。戻る操作では、通知の一覧に戻る。
  - どちらも、本体がすでに動いているときと冷えた起動のときで、結果を同じにする。
- これは、既存のクライアントで最も繰り返された不具合への対策である。Tusky は、アカウントの切り替えと画面の作り直しの競合でタイムラインを壊した (#3696)。Pachli は、「今のアカウント」を読む書き方を数か月かけて取り除いた (#964、#1431、#1732)。

### 4. 秘密の置き場所と、トークンの更新

- アクセストークン、refresh token、Push の鍵は、iOS ではアプリと拡張機能が共有する Keychain の項目に、Android では Keystore で守った領域に置く。
- iOS では、最初のロック解除の後から読め、この端末だけに属し、iCloud キーチェーンで同期しない属性にする。ロック中に通知を復号するためと、バックアップの復元や同期で、別の端末に Push の鍵と refresh token が移らないようにするためである。
- `my` の refresh token は使うたびに替わり、使い済みのものを出すと、そのトークンの系列ごと失効する (my の authentication の文書)。系列が失効すると、Push の購読も終わる。そのため、トークンの更新は、すべてのプロセスを通じて一度に 1 つにする。
  - 更新は、プロセスをまたぐ排他の下で行う。排他を取ったら Keychain を読み直し、ほかのプロセスがすでに更新していれば、それを使う。新しいトークンは、受け取ったらすぐに保存する。
  - Notification Service Extension は更新しない。時間とメモリの上限があり、打ち切られて新しいトークンを失うおそれがあるからである。手元のアクセストークンが切れていれば、中身のない通知を出さず、ADR-0005 §4 の代わりの表示にする。
  - Share Extension は、利用者が操作している間だけ、排他の下で更新してよい。
  - Android では、すべての入口が本体のプロセスで動くので、プロセスの中の排他で足りる。
- refresh token が切れたとき (30 日使わなかったとき) は、Push の購読も終わっている。次に本体を開いたときに、そのアカウントのサインインのやり直しを求め、通知が止まっていたことを伝える。

### 5. 拡張機能用のアカウントの文脈

- iOS の拡張機能が持つアカウントは、保存所を含まない小さな文脈である。中身は、アカウントの ID、サーバーの origin、表示の名前、トークン、Push の購読の ID と鍵である。
- 秘密は Keychain に、それ以外はアプリと拡張機能の共有の場所の小さな記録に置く。書くのは本体だけで、拡張機能は読むだけである。
- 通知の購読の ID からアカウントを引く対応も、この記録に置く (ADR-0005 §5)。

### 6. サインアウト

サインアウトは、次の順で、そのアカウントのものをすべて片付ける。

1. 送信待ちのもの (ADR-0008 §6) が残っていれば、捨ててよいかを利用者に確かめる。
2. サーバーでトークンを失効させる。`my` では、これで Push の購読も終わる。通信できないときは、失効の要求を残して後で送り、手元の片付けは先に進める。
3. Keychain の秘密と §5 の記録から、そのアカウントを消す。
4. そのアカウントの仕事 (WorkManager の仕事、background URLSession の転送) と送信待ちのものを取り消す。
5. 出している、そのアカウントの通知を消す。
6. アカウントの組と保存所を捨てる。

- サインアウトの後に届いた、知らない購読の通知は、iOS ではアカウントの名前を出さない代わりの表示にし、Android では出さない。
- 仕事や通知の操作が、アカウントがもうないことに気づいたら、再試行せずに終わり、その通知を消す。

## 採らなかった案

- 各画面が自分で入口を処理する: 入口ごとの実装は小さく見える。しかしアカウントの決定、検査、戻る操作の組み立てが画面ごとに散らばり、切り替えの競合を防げない。
- 「今のアカウント」を 1 つの共有の値として持ち、データの層が読む: 書くのは簡単である。しかし上の不具合をそのまま招く。
- 共有とリンクは、いつも表示中のアカウントで開く: 手順が 1 つ減る。しかし、利用者が意図しないアカウントで投稿や操作をすることになる。
- どのプロセスも自由にトークンを更新する: 拡張機能がいつでも新しいトークンを使える。しかし同時の更新で系列ごと失効し、利用者はサインアウトされ、通知も止まる。
- 拡張機能はどれも更新しない: 排他が要らない。しかし、アクセストークンが 1 時間で切れるので、本体を 1 時間開かなかった後の共有がほとんど失敗する。

## 見直す条件

- OS が、拡張機能のメモリや時間の上限を公表したか、大きく変えたとき。
- `my` が、refresh token の扱い (使うたびに替える、使い済みで系列を失効させる) を変えたとき。
