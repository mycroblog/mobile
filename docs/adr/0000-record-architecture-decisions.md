# ADR-0000: ADR と文書と作業の進め方

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. サーバーの作法に揃える

このリポジトリは、サーバー `my` の [ADR-0000](https://github.com/mycroblog/my/blob/main/docs/adr/0000-record-architecture-decisions.md) と同じ作法で運用する。両方を行き来するエージェントと決定者が、リポジトリごとに作法を切り替えずに済むようにするためである。以下は、そのうちこのリポジトリで特に効く点と、モバイルに固有の点だけを書く。

- ADR には、判断、その理由 (採らなかった案を含む)、見直す条件だけを書く。主題ごとに 1 ファイルにする。
- `Accepted` と `Rejected` にするのも、Accepted の結論を変えるのも、決定者だけである。
- リポジトリのファイルは「今」を記述する。経緯はコミットと PR に書く。
- 調査 (spike) の報告は Issue のコメントに書き、試作はマージしないブランチに置く。
- 設計文書は日本語で書く。コード、識別子、コミット、PR のタイトルは英語で書く。コミットは Conventional Commits に従う。
- ボーイスカウトルール: 作業中に見つけた壊れた箇所は、担当の範囲の外でも放置しない。小さく直せるものは本題と別のコミットで直して PR に書き、直せないものは Issue にする。
- エージェントの挙動は、枠 → 道具 → 関門 → 文章の順に守る。規則は失敗のメッセージに置き、上で済むものを文章に書かない。

### 2. 番号と参照

番号はこのリポジトリで独立させる。サーバーの ADR は `my ADR-0090 §3` のように、リポジトリ名を付けて引用する。

### 3. タスクとリポジトリの境界

- タスクは `mycroblog/mobile` の Issue と Milestone で管理する。
- サーバーの変更が要るときは、こちらで回避策を作らず、`mycroblog/my` に Issue を立てる。サーバーの API 仕様の不足や誤りも同じ扱いにする。
- 1 つの機能は、iOS と Android の実装を同じ PR に入れる (ADR-0002 §4)。

## 採らなかった案

- このリポジトリ独自の作法を作る: モバイルに合わせた最適化はできるが、2 つのリポジトリを行き来するたびに規則を切り替えることになり、その費用のほうが大きい。

## 見直す条件

- `my` の ADR-0000 の結論が変わったとき。追従するかを決める。
