# ADR-0005: 通知の中継サーバー

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. Web Push を受けて APNs と FCM に流す

- サーバーは標準の Web Push (RFC 8030、本文の暗号化は RFC 8291 の `aes128gcm`、送り手の認証は VAPID) で、プロジェクトが運営する中継サーバーに送る。
- 中継サーバーは、受けたものを APNs と FCM に流す。
- アプリは購読を作るとき、中継サーバーの URL を購読の宛先 (endpoint) としてサーバーに登録する。

こうする理由は、アプリが相手にするのが `my` だけではないからである。標準の Web Push を話す、どの実装からも通知を受けられる。サーバーにも、APNs と FCM の資格情報を持たせずに済む。

### 2. 中継サーバーは本文を読めない

- 暗号化の鍵の組は端末が作り、公開鍵と認証の秘密だけをサーバーに渡す。
- 中継サーバーは暗号文をそのまま運ぶ。復号は端末で行う (iOS は Notification Service Extension、Android は FCM の受け手)。
- 中継サーバーが知るのは、端末のトークン、送り手、届いた時刻だけである。これを記録として残す期間は、運営を始めるときに決める。

### 3. 置き場所と言語

中継サーバーは、このリポジトリの `relay/` に Go で置く。アプリと中継サーバーの変更を 1 つの PR にでき、サーバーと同じ道具を使える。APNs と FCM の資格情報は、デプロイ先の秘密の置き場所に置き、リポジトリには入れない。

### 4. 本文の大きさは spike で確かめる

Web Push の本文は最大 4096 バイトある。これを base64 にして APNs と FCM (上限はどちらも 4KB) の本文に入れると、上限を超えうる。中継サーバーを作る前に、`my` と主要な実装が実際に送る本文の大きさを測り、超えるときの扱いを決める。

## 採らなかった案

- 各サーバーが APNs と FCM に直接送る: 中継サーバーが要らない。しかし、すべての実装に公式アプリの資格情報を配ることになり、実際には成り立たない。
- 中継サーバーが復号して本文を整える: 通知の見た目を中継サーバーで作れる。しかし、すべての利用者の通知の中身が中継サーバーを通ることになる。

## 見直す条件

- 本文の大きさが §4 の上限を常に超え、端末が中身を取りに行く形が必要になったとき。
- 中継サーバーの運営の費用か負荷が、無視できなくなったとき。
