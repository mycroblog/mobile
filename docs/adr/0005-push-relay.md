# ADR-0005: 通知の中継サーバー

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. Web Push を受けて APNs と FCM に流す

- サーバーは標準の Web Push (RFC 8030、本文の暗号化は RFC 8291、送り手の認証は VAPID) で、プロジェクトが運営する中継サーバーに送る。
- 中継サーバーは、受けたものを APNs と FCM に流す。
- アプリは購読を作るとき、中継サーバーの URL を購読の宛先 (endpoint) としてサーバーに登録する。

こうする理由は、アプリが相手にするのが `my` だけではないからである。標準の Web Push を話す、どの実装からも通知を受けられる。サーバーにも、APNs と FCM の資格情報を持たせずに済む。

### 2. 中継サーバーは本文を読めない

- 暗号化の鍵の組は端末が作り、公開鍵と認証の秘密だけをサーバーに渡す。
- 中継サーバーは暗号文をそのまま運ぶ。復号は端末で行う (iOS は Notification Service Extension、Android は FCM の受け手)。
- 中継サーバーが知るのは、端末のトークン、送り手、届いた時刻だけである。これを記録として残す期間は、運営を始めるときに決める。
- 鍵の組と認証の秘密は、購読ごとに端末の安全な保存場所に置く (ADR-0007 §4)。

### 3. 置き場所と言語

中継サーバーは、このリポジトリの `relay/` に Go で置く。アプリと中継サーバーの変更を 1 つの PR にでき、サーバーと同じ道具を使える。APNs と FCM の資格情報は、デプロイ先の秘密の置き場所に置き、リポジトリには入れない。

### 4. 本文が載らないときと、復号できないとき

- Web Push の本文は、4096 バイトの 1 つの記録までである。これを APNs と FCM の本文 (上限はどちらも 4KB) に文字列として入れると、符号化によっては上限を超える。ただし実際の `my` の本文は、通知の ID・種類・表示の文・言語・Web クライアントのパスだけで、上限よりずっと小さい。
- 中継サーバーは、暗号文が載るときは載せて送る。載らないときは本文を落とし、どの購読に通知が来たかだけを送る。端末はそれを受けて、そのアカウントの通知を API で取りに行く。
- iOS では、復号できないとき、取りに行けないとき (アクセストークンが切れているとき。ADR-0007 §4)、打ち切りの時間が来たときは、中身のない通知を出さない。代わりに、アカウントの名前と「新しい通知」という表示にする。
- Android では、先に通知を出し、取りに行った後で同じ通知を書き換える (ADR-0010 §7)。

### 5. 宛先の URL は、中継サーバーの不透明な登録の ID にする

- 端末は、アカウントの購読ごとに中継サーバーに登録し、不透明な登録の ID を受け取る。購読の宛先の URL は、その登録の ID だけを含む。中継サーバーは、登録の ID を、端末のトークンとそのアカウントのサーバーの VAPID の公開鍵に結びつけて持つ。
- 中継サーバーは、登録した VAPID の公開鍵で署名されていない送信を拒む。宛先の URL を知っただけでは、ほかの者は端末に送れない。
- 端末は、受けた通知がどのアカウントのものかを、登録の ID で決める (ADR-0007 §5)。本文の中身 (アクセストークンなど) でアカウントを推測しない。Web Push の本文の形は実装ごとに違い、`my` の本文にはアカウントを示すものがない。
- 登録の ID は、アカウントごとに別にする。`my` は、同じ宛先の購読を置き換えるので、宛先がアカウントの間で同じだと、片方の購読が消える。
- 端末のトークンが変わったときは、中継サーバーの登録だけを更新する。サーバーごとの購読は作り直さない。

### 6. 本文の符号化の方式で拒まない

- 中継サーバーは `Content-Encoding` を見て拒まない。そのヘッダとともに運ぶ。
- 端末は、RFC 8291 の `aes128gcm` と、それより古い草案の `aesgcm` の両方を復号する。`my` は `aes128gcm` で送るが、Mastodon は今も `aesgcm` で送る。
- `aes128gcm` を拒む中継サーバーで、GoToSocial からの通知が壊れた例がある (Ice Cubes #2267)。

### 7. Web Push のヘッダの写し方

- 届いた送信は、どれも利用者に見える通知になる。そのため、APNs と FCM の優先度は、送り手の `Urgency` によらず高くする。
- `TTL` は、APNs と FCM の有効期限に写す。
- `Topic` は、APNs と FCM の、同じ通知をまとめる鍵に写す。

### 8. 通知を切った利用者の購読

利用者が OS の設定でアプリの通知を切ったら、本体は次に動いたときに、サーバーの購読を消す。通知を入れ直したら、購読を作り直す。FCM は、通知を出さない優先度の高い送信を続けると、以後の優先度を下げるからである。また、届けない送信をサーバーと中継サーバーに続けさせないためである。

## 採らなかった案

- 各サーバーが APNs と FCM に直接送る: 中継サーバーが要らない。しかし、すべての実装に公式アプリの資格情報を配ることになり、実際には成り立たない。
- 宛先の URL に端末のトークンを入れる: 中継サーバーに登録の表が要らない。しかし、すべてのサーバーが端末のトークンを知り、URL を知った者が誰でも端末に送れる。トークンが変わるたびに、すべてのアカウントの購読を作り直すことになる。
- 本文のアクセストークンでアカウントを照合する: 宛先の URL に何も足さずに済む。しかし本文の形は実装ごとに違い、`my` の本文にはトークンがない。
- 中継サーバーが復号して本文を整える: 通知の見た目を中継サーバーで作れる。しかし、すべての利用者の通知の中身が中継サーバーを通ることになる。

## 見直す条件

- §4 の、本文を落として取りに行かせる送り方が、通知の大半を占めるようになったとき。
- 中継サーバーの運営の費用か負荷が、無視できなくなったとき。
- `my` が、Web Push の本文の形を、安定を約束した契約として文書にしたか、変えたとき。
