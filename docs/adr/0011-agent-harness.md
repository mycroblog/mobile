# ADR-0011: エージェントのハーネス

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 道具はこのリポジトリに薄く持つ

- エージェントが作業を進める道具 (Issue を取る、作業の文脈を集める、検査する、PR を開く、Merge Queue に入れて追う、アプリを操作する) は、このリポジトリに置く。
- サーバーの `agentkit` は使い回さない。サーバーとモバイルでは、扱う物の事情が違うからである。サーバーは 1 つの言語の層とモジュールで、ブラウザで確かめる。モバイルは 2 つの OS で、シミュレータ、エミュレータ、実機で確かめる。
- 道具は、要るものだけを要るときに足す。1 つの道具は 1 つの入口で使い、古い手段は残さない (my ADR-0000 §6 の「道具」)。

### 2. 役割

役は人格ではなく、持つ知識と見るものの違いで分ける (my ADR-0169 §2、my ADR-0170 §1 と同じ考え)。

| 役 | すること | 見ないもの |
| --- | --- | --- |
| iOS の実装、Android の実装 | 1 つの Issue のその OS の側を実装し、1 つのコミットで終える | なし |
| iOS のテスト、Android のテスト | Issue の完了の条件と、公開された部品の使い方からテストを書く | 実装 |
| iOS の相談役、Android の相談役 | OS の API と指針を一次資料で調べて答え、出典の付いた知識を育てる。コードは書かない | なし |
| iOS の評価役、Android の評価役 | 動いているアプリを操作し、その OS の指針と、§3 の変化への耐性で判定する | ソース、作った過程 |
| iOS の散策役、Android の散策役 | 目的を持たずにアプリを歩き、止まった所・迷った所・画面をまたいで話が切れた所を報告する | ソース、作った過程、課題 |
| 揃いの確認役 | 両 OS で同じ課題を操作した記録を並べ、ADR-0002 §6 の「揃えるもの」が欠けていないかだけを見る | ソース、見た目の違い |
| 定型の作業 | 判断の要らない作業 | なし |

- テストの役が実装を読まないのは、実装に合わせたテストではなく、求めたことを確かめるテストにするためである (my ADR-0170 §2)。
- 評価役、散策役、揃いの確認役は、毎回新しい文脈で動く。作った過程を知ると、作った側の見方で判断するからである。
- 相談役を置くのは、OS の API と指針についての記憶に頼った判断が、この設計の段階で繰り返し誤ったからである (Hilt の寿命、Android の最小の版の理由、iPhone Duo の振る舞い)。OS に頼る判断の前には、相談役に聞く。相談役は、自分で読んだ一次資料のない知識を足さない。
- 中継サーバーの役 (Go) は、中継サーバーに着手するときに足す。

### 3. 評価はアプリを操作して行う

- 評価役と散策役は、シミュレータとエミュレータで動くアプリを 1 手ずつ操作する道具を使う。1 手ごとに、画面のアクセシビリティの木 (要素の役割と名前) とスクリーンショットを返す。
- 道具は、次の変化を起こせる。モバイルの画面の良し悪しは、静止した 1 枚ではなく、これらに耐えるかで決まるからである。
  - 操作 (タップ、入力、スクロール、戻る)
  - 外からの入力 (リンク、共有、通知)
  - 大きさの変化 (iPhone Duo の開閉、回転、iPad と Android のウィンドウの大きさの変更、折りたたみ)
  - 外見の設定 (ダークモード、文字の大きさ、右から左の言語)
  - 寿命 (バックグラウンドへの移動、プロセスの終了と復帰)
- 道具の下回りは、OS ごとのテストの仕組みを常駐させた自前の受け手と、OS の道具にする。
  - iOS は、XCUITest の受け手と `simctl`、`devicectl` を使う。iPhone Duo の開閉だけは、Apple の公開の道具に手段がないので idb (MIT) を使う。
  - Android は、UI Automator の受け手と `adb` (エミュレータのコンソールを含む) を使う。
  - §3 の変化をすべて起こせたのは、この組み合わせだけだった。画面の木には要素の役割と階層があり、共有の画面や通知のような OS の画面にも届く。1 手は Android で 0.4 秒、iOS で 1.5 秒ほどだった。
  - いずれも Xcode 27.2 の iOS 27.2 シミュレータと、Emulator 37.3 の Android 17 で試した結果である (#15 の報告、2026-11-27 に確認)。
- 1 手は、画面の木が 2 度続けて同じになってから返す。アイドルを待つだけでは、前の画面を返すことがあったからである。

### 4. Issue の進め方

- 進め方は 1 本のワークフロー (スキル) にする。Issue を取る、作業の場所とブランチを作る、役に割り振る、検査する、PR を開く、Merge Queue に入れてマージまで追う、片付ける、閉じる、までを含む。納品の単位はゴールである (ADR-0000 §1、my ADR-0000 §5)。
- 1 つの機能は、API の生成を先に済ませ、両 OS の実装の役を並行で走らせ、それぞれをテストの役に渡す。
- 画面の変更は、OS ごとの評価役と揃いの確認役を通してから、決定者に見せる。
- spike の報告は Issue のコメントに書き、コードはマージしないブランチに置き、結論を ADR に書く (ADR-0000 §1)。

### 5. 知識

- 役ごとに知識の置き場所を持つ。索引、決めたこと、良い例に分ける。
- 決定者の訂正は、その役の決めたことの 1 行になる。同じ訂正が 2 度目になったら、検査にすることを提案する (my ADR-0170 §6)。
- 相談役の知識の 1 行は、出典と確認日を持つ。
- 知識のファイルの大きさには上限を置き、検査で守る。必要なときに読まれるものが、際限なく膨らまないようにするためである (my ADR-0000 §6)。

### 6. 権限と hooks

- エージェントに許す操作は、許可の一覧に書く。force push、管理者の権限でのマージ、秘密のファイルの読み取りは拒む。
- 役ごとの制限 (テストの役が実装を読めない、評価役がソースを読めない) は、hooks で強制する。拒んだときのメッセージで、代わりに使えるものを言う。

## 採らなかった案

- サーバーの `agentkit` を使い回す: 2 つのリポジトリで道具と手順が揃う。しかしサーバーの層とモジュール、Web の確かめ方に結びついていて、2 つの OS と端末の事情を足すと、両方の道具が重くなる。
- 評価をスクリーンショットだけで行う: 道具が簡単である。しかし、操作への反応、大きさの変化、寿命、読み上げを判断できない。
- 評価役を両 OS で 1 つにする: 役の数が減る。しかし判断の基準 (HIG と Material 3) が違い、知識が混ざる。
- 両 OS で 1 つの操作の道具 (Maestro) を使う: 書き方が 1 つになる。しかし iPhone Duo の開閉、ウィンドウの大きさ、文字の大きさ、Android の右から左と共有を起こせず、iOS の画面の木に要素の役割がない。1 手も 1 秒から 7 秒ほどかかり、OS の道具を横に置くことになる。
- iOS を AXe で操作する: 1 手が最も速い (0.5 秒ほど)。しかし GPL-3.0 で、入力の空白を落とし、共有の画面と拡張を木に出さない。

## 見直す条件

- `agentkit` がサーバーから独立し、モバイルの事情を持てる形になったとき。
- 操作の道具で確かめられない不具合が、繰り返し出荷されたとき。
- Apple の公開の道具で iPhone Duo の開閉ができるようになったとき、または idb がその版の Xcode で動かなくなったとき。
