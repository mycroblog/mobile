# ADR-0012: 作業の資源

- Status: Proposed
- Date: 2026-11-28
- Deciders: @rosylilly
- Issue: #38

## Decision (決定)

### 1. 資源は、仕事が動く場所ごとに予算として扱う

エージェントの仕事は、次の場所の資源を使う。どの場所にも上限がある。仕事を割り振る前に、その仕事がどこでどれだけ使うかを見積もり、上限に収まる分だけを動かす。

| 場所 | 限られているもの |
| --- | --- |
| 手元の Mac | CPU (8 コア) とメモリ (16 GB)。決定者が同じ Mac を使う |
| CI | macOS のランナーの時間 (iOS のジョブは 1 回 30〜50 分) と、同時に走るジョブの数 |
| 決定者 | 注意と時間。許可の確認、異常への気づき、片付けの指示に使わせない |

手元の Mac での見積もりは、次のとおりである (2026-11-28 の `ps` の値と `gradle.properties` から)。

| 仕事 | メモリ | CPU |
| --- | --- | --- |
| OS と決定者のアプリ | 常に 5〜6 GB | |
| iOS のビルド 1 つ | 3〜4 GB | 8 コアを使い切る |
| Gradle のビルド 1 つ | 3〜5 GB (ヒープの上限 4 GB) | 8 コアを使い切る |
| シミュレータ 1 台 | 2〜3 GB | |
| エミュレータ 1 台 | 2〜4 GB | |
| 手元の my | 1 GB | |

仕事に使えるのは、残りの 10 GB ほどである。

### 2. 手元の Mac には、コンパイルの席と端末の席を 1 つずつ置く

- コンパイル (xcodebuild、Gradle) は、Mac 全体で同時に 1 つまでにする。
  - 1 つで CPU を使い切るので、2 つを並べても速くならず、互いを遅くし、メモリを取り合う。
  - 並行するサブエージェントやセッションのコンパイルは、席が空くのを待つ。
- 起動した端末 (シミュレータ、エミュレータ) は、Mac 全体で同時に 1 台までにする。
- コンパイル 1 つと、端末 1 台と、手元の my は、同時に動いてよい。合わせて 10 GB ほどで、§1 の予算に収まる。
- 軽い仕事 (読む、書く、lint、文書の検査、ハーネスのテスト) は、席を取らずに並べてよい。
- Gradle はデーモンを残さず、Kotlin も Gradle の中でコンパイルする。席を返したあとも、デーモンがメモリを持ち続け、次のコンパイルが予算に収まらなくなるからである。
- 席は、持ち主のプロセスが生きている間だけ有効である。
  - 持ち主が死んだ席は、次に取る者が引き継ぐ。引き継ぐ者は、席に記録された端末を落としてから使う。
  - 端末の席は、操作の道具 (ADR-0011 §3) が 15 分使わなければ、同じように引き継げる。
- 両方の席が要る仕事は、コンパイルの席を返してから端末の席を取る。片方を持ったままもう片方を待たないので、互いに待ち合って止まることがない。
- CI では席を取らない。ジョブごとにランナーが別のマシンだからである。

### 3. 手元の検査は変えた所だけを確かめ、CI はすべてを確かめる

- 手元の検査は、`origin/main` からの変更が触れた領域だけを確かめる。その仕事が使う資源が、変更の大きさに見合うようにするためである。
  - 決まりの検査 (ツールの版、文書、ハーネス) は軽いので、いつも確かめる。
  - 両アプリが共有する物 (API の文書、正解のデータ) と、検査の仕組み自身 (スクリプト、タスク、CI) は、すべての領域に効く。これらが変わったら、すべてを確かめる。
- 手元の検査で起動する端末は、iOS のテストのシミュレータ 1 台だけにする。iOS のテストは、どの層もシミュレータで動くからである。
- アプリをすべての端末の種類で起動する確認と、操作の層は、CI で確かめる。手元で毎回すべての端末を起動しても、CI が同じことを確かめ直すからである。
- CI は、Merge Queue で、すべての領域とすべての端末の種類を確かめる (ADR-0006 §3)。

### 4. 端末は、検査と操作の道具だけが起動する

- エージェントがシミュレータとエミュレータを起動し操作するのは、検査 (`task`) と操作の道具 (ADR-0011 §3) だけにする。どちらも §2 の席を取る。
- 汎用のシミュレータ操作の道具は拒む。席を取らずに端末を起動し、落とさずに残したからである。
- 操作の道具を使う役は、終わるときに道具を止めて端末を落とす。

### 5. 異常は、決定者より先にエージェントが見つける

- セッションが手を止めるとき、持ち主のいない端末が動いていれば、エージェントにそれを片付けさせる。
- バックグラウンドのエージェントは、決定者の許可を待って止まってはならない。検査は、引数なしの 1 つのコマンドで、許可の一覧に入っている。

## 採らなかった案

- 仕事を Mac 全体で 1 つずつ動かす: 作りは最も簡単である。しかしコンパイルと端末は使う資源が違うので、並べて収まるものまで待たせる。
- 空きメモリを見て、動かすかを都度決める: 予算を細かく使える。しかし §2 の 2 つの席で、すでに予算に収まる。見積もりが外れたと分かってから足せばよい。
- 手元では端末を一切起動しない: 最も軽い。しかし iOS のテストがどれも手元で回らなくなり、手元の反復が回らない (ADR-0006 の採らなかった案と同じ理由)。
- 持ち主のいない端末を、hook で自動で落とす: 漏れは必ずなくなる。しかし、使っている最中の操作の道具の端末まで落とす。

## 見直す条件

- §2 の席を守っていても、手元の Mac で swap が使われたとき。§1 の見積もりを測り直し、席の数か Gradle のヒープを見直す。
- 手元の Mac の CPU やメモリが変わったとき。
- 手元の検査が通ったのに CI で落ちる変更が、繰り返し出たとき。§3 の領域の分け方を見直す。
