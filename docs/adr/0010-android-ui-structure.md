# ADR-0010: Android の画面の構成と UI の制御

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. Google の推奨の形に従う

- Google の設計の推奨 (developer.android.com の Architecture recommendations) に従う。
  - 本体の Activity は 1 つにし、画面は Compose で書く。
  - 状態は画面ごとの ViewModel が 1 つにまとめて持ち、UI は意図を送るだけにする (単方向)。
  - ViewModel から UI へ一度きりの出来事を送らず、状態として表す。
- 独自の枠組みを足さない。エージェントの知識と公式の文書のずれを小さくするためと、OS の更新に追いつく費用を Google に持たせるためである。

### 2. ナビゲーションは Navigation 3 で、戻る操作の積み重ねをアプリが持つ

- Navigation 3 を使う。Navigation 2 系は保守だけの段階に入った。
- 戻る操作の積み重ねは、アプリが持つ型の付いたキーの並びである。キーは小さく保存でき (ID とアカウントだけ)、プロセスが終わった後もそこから戻せる。
- アカウントごとに、最上位の行き先ごとの積み重ねの組を持つ (ADR-0007 §3)。タブやアカウントを移って戻ったときに、前の位置が残るようにするためである。
- 予測型の戻る操作 (predictive back) に、それを持つすべての版で対応する。Android 13 から 15 では opt-in で有効にする。Android 16 以降で API 36 を対象にすると既定で有効になり、古い戻る操作の受け口は呼ばれない。

### 3. 外からの入力の受け方

- リンクと通知のタップは、画面を持たない入口で受ける。入口は ADR-0007 §2 の行き先の値に変え、アカウントを決めて (ADR-0007 §3) から本体の Activity に渡す。本体がすでに動いているときも、冷えた起動のときも、結果は同じにする。
- URL とカスタムスキームの読み取りは、両 OS で揃えた文法 (ADR-0007 §2) を実装したアプリ自身の読み手で行う。Navigation 3 には、読み取った後のキーだけを渡す。
- 共有は、本体のタスクではなく、共有した側のアプリのタスクの上に、独立した画面として開く。Android の共有の作法であり、利用者が本体で開いていた画面を置き換えないためである。その画面で、アカウントを選び (ADR-0007 §3)、投稿を書く。
- 通知の操作 (返信・ふぁぼ) は画面を開かず、受け手から消えない仕事 (ADR-0008 §6) に渡す。通知のタップから受け手を経て画面を開く形 (トランポリン) は OS が禁じているので使わない。

### 4. 画面の構成は幅と高さの区分で変える

画面の構成は、ウィンドウの幅と高さの区分 (window size class) で切り替える。折りたたみの端末の開閉、タブレット、デスクトップのウィンドウの大きさの変更でも同じ規則で動く。API 36 を対象にすると、幅 600dp 以上の画面では、向きと大きさの変更の制限を OS が無視する。そのため、どの大きさでも成り立つ画面にする。

| 区分 | ナビゲーション | 内容 |
| --- | --- | --- |
| 幅が compact | 下端のナビゲーションバー | 1 列。投稿を開くと積み重ねに積む |
| 幅が medium | ナビゲーションレール | 1 列 |
| 幅が expanded 以上 | ナビゲーションレール (Material 3 の現行の指針に従う形) | 一覧と詳細の 2 列。large 以上では補助の列を足せる |
| 高さが compact (横向きの電話など) | 幅の区分に従う | 幅によらず 1 列 |

- 一覧と詳細の 2 列 (タイムラインとスレッド、通知とその投稿) は、Material 3 の adaptive の部品で作る。幅が変わって 2 列と 1 列を行き来しても、開いている投稿は失わない。
- 折りたたみの端末のヒンジや姿勢 (テーブルトップなど) の扱いは、adaptive の部品の既定に任せる。独自の姿勢の表示は、要る機能が出てから決める。
- 本体の複数のインスタンス (複数のウィンドウ) は、今は開けない。iOS と違い、Android では一般的な作法ではないためである。
- 最上位の行き先の項目と順番は、ADR-0002 §6 に従う。
- ナビゲーションバーには、Material 3 の上限の 5 項目までを載せる。載らない項目は、残りをまとめた行き先から開く。レールは全項目を同じ順に並べる。どの項目をバーに載せるかは、実装で決める。
- 投稿の入口は、Material 3 の作法に従った浮かぶボタンにする。

### 5. 部品の組み立ては Hilt で、アカウントは Hilt の独自の部品にする

- アプリ全体の部品、ViewModel、WorkManager の仕事の組み立ては Hilt で行う。Google の推奨であり、ViewModel と WorkManager とのつなぎを持っている。
- アカウントの組 (ADR-0007 §3) は、アプリ全体の部品の下に置く Hilt の独自の部品 (custom component) にする。アプリの登録所が、サインインのとき (と、冷えた起動で保存から戻すとき) に作り、サインアウトのときに捨てる。
- Hilt の独自の部品は、ViewModel や Worker の部品の親にはなれない。そのため ViewModel は行き先のキーの、Worker は入力のアカウントの ID で、登録所からアカウントの組を引く。登録所は、どのプロセスでも、保存したものからアカウントの組を作り直せる。

### 6. モジュールの分け方

- 機能のモジュールは、行き先のキーだけを出す側と、実装の側に分ける。機能の実装は、ほかの機能の実装に依存しない。
- 共通の部品 (ドメインの型、API、データ、デザインシステム) は機能に依存しない。
- 依存の向きはモジュールの宣言で強制し、宣言で表せない規則は検査にする。

### 7. 通知を受けたとき

- FCM の受け手は、数秒のうちに復号して通知を出す (ADR-0005)。取り直しが要るときは、先に通知を出し、取り直した後で同じ通知を書き換える。すぐに走る仕事には割り当ての上限があり、後回しにされうるからである。
- 優先度の高いメッセージで通知を出さないと、FCM が以後の優先度を下げる。そのため、本文がなくても必ず通知を出す (ADR-0005 §4)。
- 通知の許可 (Android 13 以降) は、通知が要る理由が分かる場面で求める。

## 採らなかった案

- Navigation 2 系の Navigation Compose: 情報が多い。しかし保守だけの段階で、新しいレイアウトの部品は Navigation 3 とつながる。
- 本体の Activity の中で外からの入力を振り分ける: Activity が 1 つで済む。しかしアカウントの切り替えの最中に画面が乱れる (Pachli #1496)。
- 共有を本体のタスクで開く: 本体の画面とつながる。しかし利用者が開いていた画面を置き換え、共有した側のアプリに戻りにくい。
- DI を手で組むか Metro を使う: アカウントの寿命を自然に表せる。しかし公式の推奨と、ViewModel と WorkManager とのつなぎから外れる。

## 見直す条件

- Navigation 3 か Material 3 の adaptive の部品が、一覧と詳細の場面の扱いを大きく変えたとき。
- 2 つのアカウントを並べて見たいという要望が多く、複数のウィンドウが要るとき。
