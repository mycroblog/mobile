# ADR-0009: iOS の画面の構成と UI の制御

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 端末ではなく、幅の区分と入れ物の大きさで画面を決める

- iPhone Duo (2026-10 発売) は、閉じると幅が compact に、開くと regular になり、内容は 2 つの画面の間を移る。iPad のウィンドウ、iPhone Mirroring、iPad で動く iPhone のアプリも、使い方の途中で大きさが変わる。iOS 27 では、端末の種類 (idiom) と向きは、レイアウトを決める材料として意味を持たない (Apple の iPhone Duo の開発者向けの文書と HIG、WWDC26 のセッション、2026-11-27 に確認)。
- そのため、画面は幅と高さの区分 (size class) と、入れ物の大きさだけで組む。端末の種類、向き、画面全体の大きさ、固定の幅で分岐しない。分岐は検査で禁じる。
- 区分は、使い方の途中でいつでも変わりうる。変わっても、開いている投稿、書きかけのもの、スクロールの位置を失わない。開閉のときにシーンが保たれるかを Apple は文書にしていないので、それに頼らず、どの変化でも §3 の保存と復元で状態を守る。

### 2. 画面の構成

| 幅の区分 | ナビゲーション | 内容 |
| --- | --- | --- |
| compact (iPhone、Duo を閉じたとき、狭いウィンドウ) | タブバー | 1 列。投稿を開くと積み重ねに積む |
| regular (Duo を開いたとき、iPad、広いウィンドウ) | サイドバー | 一覧と詳細の 2 列 |

- 最上位は、幅に応じてタブバーとサイドバーを切り替える、OS のタブの入れ物にする。regular の幅では、HIG の勧めのとおり階層を 1 段多く見せる。タイムラインとスレッド、通知とその投稿、検索の結果と開いた投稿を並べる。
- 一覧と詳細の 2 列は、タブの中に入れる。一覧と詳細を持つ行き先は、タブごとに 2 列の分割表示を持つ。幅が変わると、OS が詳細を積み重ねと詳細の列の間で移す。
  - Duo の開閉、内側の画面の回転、iPad のウィンドウの大きさの変更で、開いている投稿、出している投稿の画面と書きかけの文、一覧のスクロールの位置、画面ごとの状態のどれも失われなかった (iOS 27.2 のシミュレータで確認、2026-11-27)。この振る舞いを Apple は文書にしていないので、§3 の保存と復元はそのまま行う。
  - Duo の内側の画面では、OS はサイドバーではなく縦のタブバーを既定にする。上の表のとおりサイドバーにするには、明示の指定が要る (Apple の iPhone Duo の Tech Talk、2026-11-27 に確認)。
  - HIG は、ナビゲーションの入れ物を、Duo の折り目をまたぐ配置の入れ物の外に置くよう求めている (HIG の Designing for iPhone Duo、2026-11-27 に確認)。
- 最上位の行き先の項目と順番は、ADR-0002 §6 に従う。タブバーには HIG の上限の 5 項目までを載せ、残りはまとめた行き先から開く。サイドバーには全項目を同じ順に並べる。どの項目をタブバーに載せるかは、実装で決める。
- 投稿の入口は、ナビゲーションバーかツールバーの項目にする。浮かぶボタンは Android の作法なので使わない。

### 3. ナビゲーションの状態は画面の外に持ち、シーンごとに 1 つにする

- シーン (ウィンドウ) ごとに、ナビゲーションの状態の持ち主を 1 つ置く。持つのは、表示しているアカウント、選んでいる最上位の行き先、各行き先の選択と積み重ね、出している投稿の画面などのシートである。どれも ADR-0007 §2 の行き先の値で表す。投稿の画面は、下書きの ID で表す (ADR-0008 §6)。
- 幅が変わって 2 列が 1 列にたたまれたときは、詳細を積み重ねに移す。1 列が 2 列に開いたときは、積み重ねから詳細を戻す。どちらでも状態は捨てない。
- シーンの状態は、行き先の値だけを保存して戻す。投稿の中身は保存所 (ADR-0008) から読み直す。
- 外からの入力 (ADR-0007 §2) を、どのシーンで開くかは ADR-0007 §3 に従う。App Intents からは、iOS 26 からの、シーンに向けて画面を動かす仕組みで受ける。

### 4. 複数のウィンドウ

- 本体のシーンを複数開けるようにする。iPad と、Duo を開いたときに使える。新しいウィンドウを開けない状態では、開く操作を OS が隠す部品で出す。
- 投稿やスレッドを、別のウィンドウで開けるようにする。ウィンドウは、それぞれ自分のナビゲーションの状態と、表示するアカウントを持つ。
- 投稿の画面を独立したウィンドウにするかは、その機能を作るときに決める。

### 5. バーと部品は OS のものだけを使う

- タブバー、ナビゲーションバー、ツールバーは OS のものだけを使い、独自に作らない。Duo の外側の画面と、内側の画面を横にしたときは、OS がバーを縦に置く。分割表示では、縦になるのは詳細の列のバーである。
- バーの項目には、アイコンと題の両方を持たせる。題だけの項目は縦のバーに置かれず、横のままになる。独自のビューの項目は、opt-in しない限り横のままになる。独自のビューの項目は、要る場面にだけ置く。
- 場所が足りないときは、投稿の入口と、バッジを持つ項目 (通知など) を最後まで残す。タブバーとツールバーのどちらを先に縮めるかは、ナビゲーションの画面ではツールバーを、投稿を書く画面ではタブバーを先に縮める。
- Duo の折り目やカメラを避けるための API (iOS 27.1 から) は、それを避ける必要がある独自の表示にだけ、版の確認の下で使う。ヒンジの角度の API は、レイアウトに使わない。

### 6. 状態の持ち方と組み立て

- 状態は Observation のモデルで持ち、シーンかアプリの水準で持ち主を決めて、環境 (environment) で渡す。画面ごとのモデルは、その画面に固有の処理があるときだけ作る。
- TCA は使わない。2.0 への移行が予告されており、reducer は main のスレッドで走る。マクロを多く使うので、ビルドも重くなる。
- モデルの初期化は軽く、副作用を持たせない。シーンの復元のたびに作られ、テストで直接作るためである。
- 部品の組み立ては、コンストラクタで明示的に渡し、DI のコンテナは使わない。組み立てる場所は、本体・Notification Service Extension・Share Extension のそれぞれに 1 か所ずつ置く。本体のアカウントの組 (ADR-0007 §3) は、アプリの水準の登録所が持つ。拡張機能は、保存所を含まない拡張機能用のアカウントの文脈 (ADR-0007 §5) だけを持つ。

### 7. パッケージと並行性

- コードはパッケージに分け、依存の向きはパッケージの宣言で強制する。
- 拡張機能が使ってよいのは、ドメインの型、API の通信、Keychain、Push の暗号、拡張機能用のアカウントの文脈だけである (ADR-0007 §1)。保存所と同期のパッケージは、本体だけが使う (ADR-0008 §5)。
- 拡張機能も使うパッケージは、特定の actor に属さず (nonisolated)、`Sendable` な値で受け渡す。UI のパッケージだけ、既定の隔離を MainActor にする。パッケージごとに既定の隔離が変わるので、どのパッケージも宣言で明示する。
- ビルドには、つねに最新のリリースされた Xcode を使う。Xcode 26 以前でビルドしたアプリは、Duo で互換の表示になり、画面の周りに余白が出る。

## 採らなかった案

- 端末の種類と向きで、iPhone・iPad・Duo のレイアウトを分ける: 端末ごとに作り込める。しかし iOS 27 では、端末の種類と向きはレイアウトの材料として意味を持たず、ウィンドウの大きさは使い方の途中で変わる。
- 独自のタブバーやバー: 見た目を作り込める。しかし Duo の縦のバー、Liquid Glass、あふれたときのメニューに、OS の更新ごとに追いつく必要がある。
- TCA: 状態とナビゲーションをテストしやすい。しかし §6 の費用がかかる。
- regular の幅では、サイドバーと一覧と詳細の 3 列の分割表示を最上位にし、compact の幅ではタブバーにする: 3 列を OS の部品 1 つで並べられる。しかし幅が変わるたびに分割表示とタブの入れ物が入れ替わり、画面の木が作り直される。モデルに持った選択と投稿の画面は残ったが、一覧のスクロールの位置と画面ごとの状態は失われた (iOS 27.2 のシミュレータで確認、2026-11-27)。選択を積み重ねに写す処理も、自分で書くことになる。

## 見直す条件

- Apple が、折りたたみの端末について新しいレイアウトの指針を出したとき。
- 通話を作るとき、Duo の外側の画面に付属の表示を出せる仕組みが、通話にも開かれたとき。
