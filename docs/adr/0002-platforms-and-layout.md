# ADR-0002: プラットフォーム・構成・共有の範囲

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 両 OS ともネイティブで実装する

- iOS は Swift と SwiftUI で書き、`app/ios` に置く。
- Android は Kotlin と Jetpack Compose で書き、`app/and` に置く。
- 最小の版は iOS 17 と Android 9 (API 28) にする。iOS 17 は Observation を使うためである。

ネイティブを選ぶのは、通知、バックグラウンドでの音声、通話の統合 (CallKit、Telecom)、スクロールの性能を、OS の一次の API で扱うためである。

### 2. 共有するのは原本と生成器であり、実行時のコードではない

両 OS で共通のものは `shared/` に置き、そこから各 OS のコードを生成する。

- API の仕様 (ADR-0003)
- メッセージのカタログ
- ブランドの色と、サーバーごとのテーマ (my ADR-0059)。§6 で揃えるものに限る
- テストの正解データ (API の応答、ストリーミングのイベント列)

実行時のロジックは、各 OS で書く。共有するのは「何が正しいか」であり、各 OS の実装がそれに合っていることは、両 OS が同じ正解データを読むテストで保証する。

### 3. 共有の置き場所は、使い始めるときに足す

`shared/` の下のディレクトリは、使う機能を実装するときに作る。通話のメディア (WebRTC) の扱いは、着手するときに調べて ADR に決める。

### 4. 機能は両 OS を同じ PR で揃える

1 つの機能の Issue は、iOS と Android の実装を同じ PR に入れる。片方だけ先に進めると、機能のずれが溜まるからである。揃えるのは §6 の「揃えるもの」であり、画面の見た目ではない。

### 5. 開発は Mac 上で行う

エージェントは Mac 上で動かし、両 OS を手元でビルドし、テストし、画面を確かめる。CI でも両 OS の検査を通す。

### 6. 見た目と操作は各 OS のガイドラインに従う

画面の見た目と操作は両 OS で揃えず、iOS は Apple の Human Interface Guidelines に、Android は Material Design 3 に従う。利用者は、その OS のほかのアプリと同じ作法を期待しているからである。それが、ネイティブで実装する理由の一つでもある (§1)。

- **揃えるもの**:
  - 機能と、できる操作
  - 振る舞い (状態の移り変わり、エラーと再試行、オフラインのときの扱い)
  - 内容 (表示する情報、文言の意味)
  - ブランドの色と、サーバーごとのテーマ
- **各 OS に従うもの**:
  - ナビゲーションの構造
  - 部品
  - 文字の体系と大きさ、余白
  - アイコン
  - 身振り (ジェスチャ) と動き
  - 触覚のフィードバック
  - システムの機能との統合 (共有、ウィジェット、通知の操作)

ブランドの色も、各 OS の色の仕組み (iOS の意味で決まる色、Material の色の役割) に当てはめて使う。OS が用意する部品を、ブランドに似せるために作り直さない。

## 採らなかった案

- 両 OS で同じデザインにする: デザインと評価が 1 つで済む。しかし、どちらの OS でも作法から外れたアプリになり、OS が更新されるたびに独自の部品を保守することになる。

- Kotlin Multiplatform でロジックを共有する: 実装は 1 回で済む。しかし Swift 側の書き味と型の表現が落ち、ビルドの構成も重くなる。共有したいのは仕様の一致であって、実装ではない。
- 片方の OS を先行させる: 早く動くものが出る。しかし機能のずれと、後から追いかける作業が溜まる。

## 見直す条件

- 正解データのテストで揃えきれない、両 OS で重複したロジックが目立ったとき。
- 最小の版を、OS の利用者の分布で見直すとき。
