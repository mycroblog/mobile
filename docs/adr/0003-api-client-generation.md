# ADR-0003: API の取り込みとクライアントの生成

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 正はサーバーのバンドルされた仕様

- サーバーの `api/openapi.yaml` (OpenAPI 3.1 の 1 ファイル、MIT) を取り込み、取り込み元のコミットを記録する。
- 仕様の変更はサーバーで行う (ADR-0000 §3)。こちらで仕様を手で直さない。
- 仕様の更新は、1 回の取り込みを 1 つの PR にし、生成物と、それに合わせた両 OS の修正を同じ PR に入れる。

### 2. 生成

- iOS は `apple/swift-openapi-generator` を使う。OpenAPI 3.1 に対応し、Apple が保守している。
- Android は Fabrikt を使い、Ktor のクライアントと kotlinx.serialization のモデルを生成する。版は固定し、上げるときは仕様の取り込みと同じく 1 つの PR にする。
  仕様の全体 (パス 374、スキーマ 714、2026-11-27 時点) を警告なしで通し、手を加えずにコンパイルできる。判別子つきの `oneOf` は sealed interface になり、実行時にも部分型として読み書きできる。出力は説明を Markdown のまま残し、タグごとのクライアントにまとまるので、エージェントが読みやすい (Fabrikt 29.2.0 で確認、2026-11-27)。
- 生成器が型にしないものは、生成物の外に薄く手で書く。エラー応答 (RFC 9457 の Problem) の読み取り、UUID と URI の直列化、知らない判別子の扱いである。
- 生成器の不具合は、生成物を手で直さず、生成器に報告するか修正を送る。Fabrikt はクエリとパスの値をパーセントエンコードしない (2026-11-27 に確認)。これは、その値を使う機能より先に直す。
- 生成物はコミットし、再生成して差分がないことを CI で検査する。エージェントが生成されたコードを読めるようにするためと、仕様の更新の影響を diff で見えるようにするためである。

### 3. ストリーミング

`/api/v1/streaming` (SSE) の読み手は、両 OS で手書きする。振る舞いはサーバーの公式のライブラリ (my ADR-0093 §6) に揃える。

- `Last-Event-ID` を送らず、再接続したことを呼び出し側に知らせる。
- 指数バックオフとジッタで再接続する。`Retry-After` に従う。
- ハートビートが 60 秒届かなければ、切って再接続する。
- 知らないイベントは捨てずに、未知のイベントとして渡す。

両 OS の実装は、同じイベント列の正解データを読むテストで一致させる。

## 採らなかった案

- 生成物をコミットせず、ビルドのたびに生成する: リポジトリは小さくなる。しかしエージェントが生成されたコードを読めず、仕様の更新の影響が見えない。
- 両 OS で 1 つの生成器を使う: 道具は 1 つで済む。しかし各 OS の一次の選択肢から外れ、生成されるコードの質が落ちる。
- openapi-generator の Kotlin 出力 (kotlinx.serialization): 仕様の全体を読めて、URL の値も正しくエンコードする。しかし判別子つきの `oneOf` が、部分型を持たない sealed class になり、実行時に読めない。生成したままではコンパイルできず、オプションと出力への手直しが要る (v7.28.0 で確認、2026-11-27)。
- 自前の生成器: この仕様が使う構文に絞れば作れる (エージェントの作業で 3〜5 日)。しかし Fabrikt が 3 点を満たすので、作る理由がない。3.1 の構文が増えるたびに保守も要る。
- Fabrikt の OkHttp のクライアント: kotlinx.serialization を選んでも Jackson に依存し、生成したモデルと組み合わせられない。

## 見直す条件

- 選んだ生成器が、サーバーの仕様で使い始めた 3.1 の構文を扱えなくなったとき。
