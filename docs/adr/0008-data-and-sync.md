# ADR-0008: データと同期

- Status: Accepted
- Date: 2026-11-27
- Deciders: @rosylilly

## Decision (決定)

### 1. 正はサーバーであり、端末のものは捨ててよいキャッシュである

- 端末に保存するものは、サーバーから取り直せる。消えて失われるのは、利用者の書いたもの (送信待ちの投稿、書きかけの投稿) だけであり、それだけは §6 で守る。
- 画面は保存所から読む。保存所に書くのは同期の部品だけで、画面は通信の結果を直接持たない。Android ではプロセスが終わった後に、iOS ではシーンが作り直された後に、画面を保存所から作り直すためである。

### 2. 投稿とアカウントは、アカウントごとに正本を 1 つ持つ

- 投稿とアカウントの記録は、(サインインしたアカウント, ID) で一意にする。同じ投稿がホーム・通知・スレッド・プロフィールに出ても、記録は 1 つである。どこで変わっても、すべての場所に同時に出る。
- タイムラインは、投稿の ID の並びだけを持つ。
- 開閉、既読の位置のような画面の状態は、正本と別に持つ。正本を取り直しても消えないようにするためである。
- 正本は、投稿の全体で置き換える。部分の更新を重ねない。`my` は、ふぁぼなどの操作のたびに、操作の後の投稿の全体を返す。

既存のクライアントの失敗は、両極にある。

- mastodon-ios は、Core Data に正規化して持ち続けた。古くなったデータと性能の低下のために、その量を大きく減らした (#1167)。
- Ice Cubes は、タイムラインごとに丸ごと保存し、投稿の正本を持たない。アカウントを切り替えた後にふぁぼの状態が失われるといった、状態が古いまま残る不具合を抱えている (#812)。

この決定は、正本を 1 つにすることと、それを使い捨てにすること (§3) の両方を採る。

### 3. タイムラインは継ぎ足さずに置き換える

- 開き直したときと、ストリーミングがつなぎ直したときは、最新のページから読み、手元の並びとつながるまで辿る。決めた数のページを辿ってもつながらなければ、手元の並びを捨てて最新に置き換える。途中の欠け目を「続きを読む」の印として残すことはしない。
  - Tusky の欠け目の印は不評で、古い穴が残った (#2938、#2831)。Pachli は、継ぎ足しをやめて置き換えにした (#43)。
  - `my` のタイムラインは、新しい側から古い側へのカーソルだけを持つ。つながるまで辿る形は、それでそのまま使える。
- 読んでいた位置は、基準にした投稿の ID と、そこからのずれで戻す。置き換えた後に基準の投稿がなければ、最新から始める。
- 保存の量に上限を設け、起動のときに刈り込む。Pachli では、バックグラウンドの刈り込みが一部の端末で走らず、問い合わせが秒単位に遅くなった (#2139)。

### 4. ストリーミングとの関係

- ストリーミングの出来事 (新しい投稿、通知、削除) は、同期の部品が受けて保存所に書く。画面はストリーミングを直接読まない。
- つなぎ直したことの知らせを受けたら、§3 の手順で読み直す (ADR-0003 §3)。
- ローカルと連合のタイムラインのストリーミングが、サーバーがそのタイムラインを止めたことで終わったときは、その行き先を出すのをやめる (ADR-0002 §6)。
- ストリーミングで届かない変化は、画面に出すときに取り直して補う。`my` のストリーミングには、投稿の編集の出来事がない。

### 5. 保存所を開くのは本体のプロセスだけである

- SQLite の保存所は、本体のプロセスだけが開く。iOS の拡張機能 (Notification Service Extension、Share Extension、ウィジェット) は、保存所を開かない。Android の受け手と仕事は、本体のプロセスで動くので、保存所を使ってよい。iOS の通知の操作も、本体のプロセスで受ける。
- iOS の拡張機能から本体に渡すもの (共有で作った送信待ちの投稿など) は、アプリと拡張機能の共有の場所に、小さなファイルかキューとして置き、本体が取り込む。
- 理由は 2 つある。1 つは、別のプロセスからの書き込みを観測する手段がないことである (GRDB の文書)。もう 1 つは、共有の場所のロックを持ったまま停止させられたプロセスが、OS に強制終了されることである (0xDEAD10CC)。GRDB の文書も、SQLite より先に平らなファイルの共有を考えるよう勧めている。

### 6. 書き込みは、消えない仕事として完遂させる

- **送信待ちのキュー**: 投稿、メディアの送信、ふぁぼ、フォローは、送信待ちのキューに冪等のキー (`my` の Idempotency-Key) とともに積む。
  - 画面には、送ったものとしてすぐに反映する。失敗したら元に戻し、理由を見せる。
  - プロセスが終わっても失われない。
- **再試行の期限**: 再試行は、最初の送信から 24 時間までにする。`my` は、同じキーの再送を 24 時間しか同じ答えにしないからである。それを過ぎて送れていないものは、自動で送らない。利用者に「未送信」として見せ、送り直すかを決めてもらう。送り直すときは新しいキーを使う。
- **大きなメディアの送信**:
  - iOS では background URLSession で送る。利用者がアプリを強制終了すると止まるので、送信待ちのキューに状態を残し、次の起動で再開する。
  - Android では WorkManager で送る。Android 14 以降で、利用者が画面を見ている間に始めた大きな送信は、利用者が始めた転送の仕事 (JobScheduler) で送ってよい。バックグラウンドからの再試行は、いつも WorkManager で行う。
- **共有からの投稿 (iOS)**: Share Extension は、自分で送り始める。
  - 本文だけの投稿は、画面を出している間に送る。
  - メディアは、共有の場所を使う background URLSession で送る。転送が終わると、OS が本体をバックグラウンドで起こすので、本体がキューを照らし合わせ、残りの投稿を送る。
  - 送れなかったときは、通知で利用者に知らせ、本体を開くと未送信として見える。
  - 本体を開くまで何も送られない形にはしない。
- **予約投稿**: 端末で時刻を待たず、サーバーの予約投稿 (my ADR-0156) で行う。OS は、端末のバックグラウンドの実行の時刻を保証しない。
- **書きかけの投稿と下書き**:
  - 投稿の画面の書きかけのものは、変わるたびに保存所に書く。画面の大きさの変化、シーンの切り離し、プロセスの終了で失わないためである。
  - 利用者が下書きとして残すものは、サーバーの下書き (my ADR-0156) に置く。Web と他の端末から続きを書けるようにするためである。

### 7. 保存の道具

- iOS は GRDB を、Android は Room を使う。どちらも正本とタイムラインの表を SQL で明示的に書け、問い合わせの結果の変化を観測できる。
- SwiftData は採らない。拡張機能の書き込みの後に画面が古いままになるという報告があり (Apple Developer Forums)、保存の形を SQL で制御しにくいためである。
- Room は Room 3 を使う。Room 3 は 2026-07-01 に安定版になり、Room 2 は保守だけの段階に入った (developer.android.com の Room のリリースノートと Android Developers Blog、2026-11-27 に確認)。

## 採らなかった案

- 保存せず、メモリだけで持つ: 作りは簡単である。しかし Android では、プロセスが終わるたびに空になる。後から保存所を足すと、すべての画面の読み方を作り直すことになる。
- すべてを正規化して長く持ち続ける: 通信は減る。しかし古いデータが残り、性能が落ちる (mastodon-ios #1167)。
- タイムラインの欠け目を印として残し、利用者に埋めさせる: 取り直す量は減る。しかし不評で、古い穴が残る (Tusky)。
- 送信待ちのものを、利用者が諦めるまで無期限に再試行する: 送れる見込みは上がる。しかし冪等のキーが 24 時間で効かなくなり、同じ投稿が二重にできうる。
- Share Extension は送信待ちを置くだけにし、本体が送る: 拡張機能の実装が小さい。しかし利用者が本体を開くまで送られず、送れたかどうかも見えない。

## 見直す条件

- §3 の置き換えが頻繁に起き、読んでいた位置を失うという苦情が続いたとき。
- `my` が、欠け目を埋めるための新しい側へのカーソルか、ストリーミングの再開の手段を持ったとき。
- `my` のストリーミングが、投稿の編集の出来事を持ったとき。
